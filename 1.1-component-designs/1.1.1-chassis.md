## Overview ^chassis-overview

The [[00-overview#^def-chassis|Chassis]] is the **initializer and message router** of the SuBot system. It provides the foundation for the plugin-based architecture where all functionality (AI profiles, tools, storage, UI) is implemented as plugins.

**Key Characteristics**:
- Initializes the system and loads all plugins
- Routes messages between plugins via pub/sub message bus
- Manages plugin lifecycle and registry
- Provides standardized interfaces for plugin communication
- Does NOT contain orchestration logic (that's the Orchestrator profile's responsibility)

**Related:** [[01-architecture#^microkernel-architecture|Micro-kernel architecture]], [[03-decisions-log#^adr-cli-primary-interface|CLI interface decision]]

## Responsibilities ^chassis-responsibilities

### What the Chassis DOES ^chassis-does
1. **System Initialization**
   - Boot the system
   - Load configuration files
   - Initialize plugin registry
   - Set up message routing infrastructure (pub/sub bus, NOT orchestration logic)

2. **Plugin Management**
   - Discover available plugins (from config + filesystem)
   - Register plugins in the plugin registry
   - Manage plugin lifecycle (init, activate, deactivate, shutdown)
   - Provide plugin-to-plugin communication channels

3. **Message Routing**
   - Route messages between plugins via message bus
   - No orchestration logic (that's Orchestrator profile's job)
   - Plugins drive their own flow

4. **Interface Provision**
   - Provide standardized interfaces for:
     - Hook registration
     - Configuration access
     - Message passing
     - State storage access

### What the Chassis DOES NOT DO ^chassis-does-not
- ❌ Orchestrate workflows ([[00-overview#^def-orchestrator|Orchestrator]] profile does this)
- ❌ Make decisions about data flow (plugins decide)
- ❌ Implement business logic (all in plugins)
- ❌ Maintain domain state (plugins maintain their own)

## Core Interfaces

### 1. Chassis Core
```python
class Chassis:
    """
    The system initializer and message router.
    Bare bones - provides interfaces, plugins do the work.
    """
    
    def __init__(self, config_path: str):
        self.config = Config(config_path)
        self.plugin_registry = PluginRegistry()
        self.message_bus = MessageBus()
        self.hook_manager = HookManager()
        
    def boot(self):
        """Initialize the system"""
        self._load_plugins()
        self._init_plugins()
        self._register_hooks()
        
    def _load_plugins(self):
        """Discover and load plugins from config"""
        for plugin_config in self.config.plugins:
            plugin = self._instantiate_plugin(plugin_config)
            self.plugin_registry.register(plugin)
            
    def _init_plugins(self):
        """Initialize all registered plugins"""
        for plugin in self.plugin_registry.all():
            plugin.initialize(self)
            
    def _register_hooks(self):
        """Let plugins register their hooks"""
        for plugin in self.plugin_registry.all():
            plugin.register_hooks(self)
    
    def route_message(self, message: Message):
        """Route message to appropriate plugins"""
        self.message_bus.publish(message)
        
    def shutdown(self):
        """Graceful shutdown"""
        for plugin in self.plugin_registry.all():
            plugin.shutdown()
```

### 2. Plugin Interface
```python
class Plugin(ABC):
    """
    Base interface all plugins must implement.
    Plugins are self-contained, drive their own logic.
    """
    
    @abstractmethod
    def initialize(self, chassis: Chassis):
        """Called during system boot"""
        pass
        
    @abstractmethod
    def register_hooks(self, chassis: Chassis):
        """Register for events this plugin cares about"""
        pass
        
    @abstractmethod
    def shutdown(self):
        """Cleanup before system shutdown"""
        pass
        
    # Plugins implement their own logic methods
    # Example:
    # def handle_new_finding(self, finding: Finding):
    #     # Plugin-specific logic
```

### 3. Message Bus
```python
class MessageBus:
    """
    Simple pub/sub message routing.
    No orchestration - just delivery.
    """
    
    def __init__(self):
        self._subscribers = defaultdict(list)
        
    def subscribe(self, event_type: str, handler: Callable):
        """Subscribe to an event type"""
        self._subscribers[event_type].append(handler)
        
    def publish(self, message: Message):
        """Publish message to all subscribers"""
        for handler in self._subscribers[message.type]:
            handler(message)
```

### 4. Plugin Registry
```python
class PluginRegistry:
    """
    Manages plugin lifecycle and lookup.
    Chassis manages this, plugins manage their own data.
    """
    
    def __init__(self):
        self._plugins = {}
        
    def register(self, plugin: Plugin):
        """Register a plugin"""
        self._plugins[plugin.name] = plugin
        
    def get(self, name: str) -> Optional[Plugin]:
        """Get plugin by name"""
        return self._plugins.get(name)
        
    def all(self) -> List[Plugin]:
        """Get all registered plugins"""
        return list(self._plugins.values())
```

   - Evaluator, Validator, Enforcer, Recommender, Orchestrator
   - Builder, Debugger, Synthesizer, Optimizer
   - Each is an independent plugin

   - Base/preset adapters provided with system
   - Generic adapter factory for dynamic tool support

3. **Methodology Handlers**
   - Load and parse methodology YAML

   - Provides interface for Security-Context Map
   - Profile state storage

5. **User Interface**
   - CLI plugin
   - (Future) Electron UI plugin

6. **Approval Handlers**
   - Human approval workflow
   - Approval UI integration

## Data Flow Control

**Chassis Role**: Message routing only - plugins drive their own flow

**Example Flow**:
```
1. User starts scan (CLI plugin)
   ↓
2. CLI plugin publishes "scan.start" message
   ↓
3. Chassis routes to subscribers:
   - Orchestrator profile receives it
   - Security-Context Map receives it
   ↓
4. Orchestrator decides what to do:
   - Orchestrator publishes "tool.invoke" message
   ↓
5. Chassis routes to Tool Adapter
   ↓
6. Tool Adapter runs, publishes "finding.new" messages
   ↓
7. Chassis routes to subscribers:
   - Evaluator profile
   - Validator profile
   - Security-Context Map
   ↓
[Plugins continue driving the flow]
```

**Key Point**: Chassis just routes. Orchestrator profile (heavily using chassis) drives workflow decisions.

## State Management

**Hybrid Approach**: 
- **Chassis manages**: Plugin registry (what plugins exist, their status)
- **Plugins manage**: Their own data, state, and logic

**Example**:
```python
# Chassis tracks plugin status
chassis.plugin_registry.get("orchestrator").status  # "active"

# Orchestrator plugin manages its own state
orchestrator.queue  # Orchestrator's internal queue
orchestrator.active_tasks  # Orchestrator's task tracking

# Validator plugin manages its own state  
validator.validated_findings  # Validator's cache
validator.false_positive_patterns  # Validator's learned patterns
```

## Boot Sequence

```
1. Load config/subot.yaml
   ↓
2. Initialize Chassis
   ↓
3. Discover plugins (from config/plugins.yaml)
   ↓
4. Load plugin modules
   ↓
5. Instantiate plugin classes
   ↓
6. Register plugins in PluginRegistry
   ↓
7. Initialize plugins (call plugin.initialize())
   ↓
8. Register hooks (call plugin.register_hooks())
   ↓
9. System ready
   ↓
10. CLI plugin activates (or other entry point)
```

## Error Handling

**Plugin Isolation**:
- Plugin errors don't crash the system
- Chassis catches exceptions, logs, notifies
- Other plugins continue operating

```python
def route_message(self, message: Message):
    for handler in self._get_handlers(message.type):
        try:
            handler(message)
        except Exception as e:
            self.logger.error(f"Plugin error: {e}")
            self.message_bus.publish(Message(
                type="system.error",
                data={"plugin": handler.plugin_name, "error": str(e)}
            ))
```

## Orchestrator Profile Relationship

**Orchestrator is the primary chassis user**:
- Receives messages from chassis
- Makes workflow decisions
- Publishes messages back through chassis
- Coordinates other profiles via chassis message bus

**Example**:
```python
class OrchestratorPlugin(Plugin):
    def register_hooks(self, chassis):
        # Orchestrator listens to many events
        chassis.on("finding.new", self.triage_finding)
        chassis.on("scan.complete", self.plan_next_actions)
        chassis.on("profile.conflict", self.resolve_conflict)
        
    def triage_finding(self, message):
        finding = message.data
        
        # Orchestrator decides what to do
        if finding.severity == "high":
            # Trigger validation
            self.chassis.publish(Message(
                type="validation.request",
                data=finding
            ))
```
